# 3 3 trust boundaries

## 3.3.1 On-Chain and Off-Chain Boundaries

Principle: only commitments, roots, proof results and necessary adjudications go on-chain; state plaintext, keys, authorization decisions and high-frequency reads and writes stay off-chain. Meeda's DA design places KZG commitments and aggregated proofs on-chain and keeps blobs off-chain; the verification configuration binds the algorithm identifier, parameter set, network identifier, contract version and challenge window, and verifiers check the corresponding data batches according to that configuration.

| Type                           | Location                                                                                      | Reason                                                                                                           |
| ------------------------------ | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| State plaintext                | Off-chain: Local / Hosted / MEFS, stored encrypted                                            | Privacy, low latency, key rotation and the cost of large objects                                                 |
| Authorization decisions        | Off-chain, enforced by Gateway                                                                | Agent requests cannot wait for on-chain confirmation every time                                                  |
| Access receipts                | Off-chain signed log, saved locally first by policy, then exported or anchored asynchronously | Decouples request handling from batch anchoring and retains a traceable record                                   |
| Audit roots                    | On-chain or a publicly verifiable system                                                      | Verifies membership and content consistency for a specified batch; does not automatically prove log completeness |
| Storage commitments and proofs | On-chain commitments / public verification material                                           | Proves that data was stored under the rules within a specific time window                                        |
| State asset registration       | On-chain, aligned with ERC-7829 by implementation                                             | Used only for objects that undergo rights confirmation, delivery or trading                                      |

State asset registration does not turn all personal memory into NFTs or make it public by default. Batch anchoring of receipts should not block the request hot path.

## 3.3.2 Plaintext, Keys, Commitments and Proofs

The six concepts below express content, capability or evidence respectively, and cannot substitute for one another during verification:

| Concept     | Definition                                                                                                                                                                           | What it can show                                                                                       | What it cannot show                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Plaintext   | The actual state content, stored encrypted off-chain by default                                                                                                                      | The content itself                                                                                     | Having a CID does not mean permanent availability or authorization                                                                      |
| Key         | Cryptographic material distinguished by purpose; the content encryption key is used for encryption and decryption, and the identity signing key is used for principal control proofs | The corresponding decryption capability or signing control                                             | Holding a key does not mean obtaining permission for a business purpose; the replacement of the two kinds of keys must not be conflated |
| Commitment  | A commitment object binding a defined algorithm, scope and content version                                                                                                           | A consistency comparison within the specified scope; the object example covers the ciphertext envelope | It is not a storage proof, does not prove the content is true, and does not guarantee that the digest is unchanged after re-encryption  |
| Receipt     | A signed record made by an issuer about a request, decision and result                                                                                                               | That the issuer made the corresponding event statement                                                 | Does not automatically prove the event actually occurred, the log is complete, or the task was accepted                                 |
| Attestation | A statement issued by a principal about an object or event                                                                                                                           | That a principal made a specific statement                                                             | A statement is not the same as the fact itself being true                                                                               |
| Proof       | Verification material provided for a defined claim                                                                                                                                   | That the specified claim holds under the conditions                                                    | Cannot broadly prove that an Agent is correct                                                                                           |

Each kind of evidence explicitly binds the proved object, the issuer and verifier, the verification method, the version, the time range and the trust conditions. Signature verification checks the binding between the signature and the record, a Merkle inclusion proof verifies membership in a specified batch, a storage proof verifies the agreed retention claim, and business acceptance executes the specified acceptance rules; the four kinds of results are recorded separately. Standards adaptation interfaces list the fields, methods and verification parameters adopted in the compatibility configuration, and verification covers only the corresponding scope.

## 3.3.3 Controlled Processing, External Side Effects and Failure Semantics

Controlled processing includes retrieval, summarization, redaction, format conversion, and TEE and compute-platform computation. The execution manifest of a processing task binds the input object versions, the purpose, the key policy, the permitted execution environments, the output location, the retention period and the resource budget. Gateway first validates the independent processing authorization and then issues short-term restricted capability to executors that meet the environment identity and policy conditions; a task that needs a TEE additionally verifies the environment attestation and the measurement values specified by policy. The compute platform carries computation tasks scheduled by resources and execution environment, and results are written back to Vault after validation against output scope and provenance rules, with input and output digests and necessary runtime evidence going into audit records.

Payments, sending messages, calling production APIs, submitting transactions and modifying third-party systems are external side effects. Before execution, the independent operation scope, purpose, target domain or payee, and amount and frequency limits signed in advance by the Owner are validated automatically, and a Checkpoint is saved; execution uses a stable `operation_id` and idempotency key, and the result goes into the business ledger and the receipt. Actions beyond the authorization or budget are rejected outright, an unknown result goes into query and reconciliation, and a clear failure is handled under preset compensation rules. Ordinary state read authorization does not include these capabilities.

Failure semantics distinguish at least:

| Failure type                                          | Retryable                                                                                        | Handling principle                                                                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity failure / invalid delegation / policy denial | A new request is formed only after valid authentication or an independent delegation is obtained | Does not touch plaintext and saves a minimal denial receipt; a log fault returns pending or failed independently                                            |
| Object not found / version conflict                   | Handled by typed conflict policy                                                                 | Does not disclose unauthorized existence; deduplicated append, field merge or retention of an isolated branch                                               |
| Storage backend unavailable                           | After querying the business ledger, retry with backoff or degrade under idempotency constraints  | Reports success only when persistence conditions are met; for an unknown result, query first                                                                |
| Local receipt save failed / recovering                | Query and recover the record by operation\_id                                                    | Keeps the actual business result; the receipt returns failed or pending independently, and business that has already succeeded is not repeated              |
| Proof delay                                           | May wait asynchronously                                                                          | Business success and proof completion are kept as separate statuses                                                                                         |
| External action failure                               | According to operation semantics                                                                 | Use idempotency keys, reconciliation and compensation                                                                                                       |
| Unknown result                                        | Stop business replay and perform only bounded queries                                            | Reconcile automatically from the operation ledger, external queries and receipts; when it cannot be determined, quarantine the operation and retain unknown |

The runtime mechanism maintains three invariants:

* An unauthorized managed request must not touch state plaintext.
* A write failure must not declare business success in a receipt.
* When the result of an external action is unknown, it must not be retried automatically without condition.
