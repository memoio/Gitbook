# 4.1 Quick Start

## 4.1.1 Your First Durable Agent Task

The first tutorial uses a local configuration of Local Vault + Gateway to perform automatic memory admission, checkpoint saving, task recovery, provenance and receipt verification, revocation of a specified Agent delegation, and export and cleanup under independent authorization. The Owner signs a delegation for the test scope in advance, and the task script runs automatically within the purpose and operation boundaries; local state saving and receipt verification are completed through the local backend, and proof anchoring runs as an asynchronous step according to configuration.

**Prerequisites**:

* A separate test directory; the user's existing working directory is not used as the cleanup target in the example;
* One user identity and one Agent DID, or clearly labeled test principals in a development environment;
* Local Vault, Gateway and SDK configuration that matches the signed service manifest;
* Test data only; the tutorial does not use a production main wallet private key;
* A fixed test namespace, dependency versions, budget limit, expected output and a restricted cleanup path.

**Client-side pre-encryption payload example**: the project requirement below, after validation by provenance and admission policy, is encrypted on the client or in a controlled environment specified by policy, producing a content reference and a ciphertext commitment. The payload and the object envelope are handled in separate layers, and ordinary runtime logs record only restricted digests and object references.

```json
{
  "kind": "project_requirement",
  "text": "Project deliverables must include provenance and acceptance records"
}
```

**Example of a persisted State Object**:

```json
{
  "schema_version": "memo.state_object/1",
  "object_id": "mem_project_a_001",
  "type": "memory",
  "owner": "did:memo:user:example",
  "namespace": "project/a",
  "version": "v_001",
  "parent_refs": [],
  "provenance": {
    "source_type": "user_input",
    "source_refs": ["source://project/a/brief"],
    "producer_agent_did": "did:memo:agent:example",
    "producer_instance_id": "instance_example",
    "producer_run_id": "run_20261016_001",
    "confirmation_status": "confirmed",
    "confirmation_method": "policy_validation",
    "confirmed_by": "did:memo:service:policy-engine",
    "confirmation_policy_ref": "policy_project_a_memory_admission_v1"
  },
  "policy_ref": "policy_project_a_v1",
  "content_ref": "encrypted://content/mem_project_a_001/v_001",
  "commitment": {
    "algorithm": "sha256",
    "scope": "ciphertext",
    "value": "<digest>"
  },
  "created_at": "2026-10-16T02:00:00Z",
  "expires_at": null,
  "proof_refs": []
}
```

`version` is an opaque, unique and immutable version identifier assigned by the server, and `v_001` is its string form; `schema_version` denotes the envelope format. `parent_refs` records only direct parent versions, and provenance and dependencies go in `provenance`. The admission fields are generated by the policy engine and bound to the admission policy; the provenance statements submitted by the client are validated against signature and dependency rules and cannot raise the admission status on their own.

`commitment.scope=ciphertext` means the digest is for the specified ciphertext envelope; re-encryption or format conversion creates a new version and records the old-to-new commitment mapping. Reference parameters come from environment configuration or persisted results, and `<digest>` is computed by the client over the encrypted envelope with the specified algorithm and then injected. `proof_refs` retains the evidence snapshot at creation, and asynchronous evidence is written to the Proof Registry by `(object_id, version)` and merged for display at read time without modifying that version.

**Automated validation rules**: when dependency object versions and recovery conditions are satisfied, the script recovers business state from the Checkpoint; a managed read by another, unauthorized Agent returns a denial; an independent export delegation exports only the objects within the permitted scope along with the allow and deny receipts; after the revocation record is persisted at the specified enforcement point, subsequent controlled requests return a denial. The manifest validation of the Memory Pack excludes namespaces not selected, the user's root key and the Agent identity private key; the recipient's content key wrapping binds the recipient, purpose and term and is verified automatically on import.

## 4.1.2 Reading and Writing State with the SDK / REST

The three access methods reuse the same semantics: the SDK encapsulates signing and schemas; REST serves service integration; and MCP serves Agent tool calls. A managed request carries the principal, instance, run, delegation, target, operation, purpose and request identifier; a write request also binds idempotency information and the expected version. The entry adapter normalizes the request and passes it into the same policy engine, and compatibility validation asserts identical authorization decisions, object versions and business statuses for the same request.

**Write interface contract**: this example updates the stable object `chk_project_a_001`, with `v_003` as the expected parent version. The request carries the business payload and the authorization context; the server generates the version, time and admission result, and the persisted object follows the envelope in Section 4.1.1. The client appends the relative path below to the Gateway base address in the registry and validates the credential audience and the service identity.

```http
POST /v1/state/objects
Authorization: Bearer <limited-token>
Memo-Request-Proof: <signed-request-proof>
Idempotency-Key: op_checkpoint_save_001
Content-Type: application/json
```

```json
{
  "request_id": "req_example_001",
  "operation_id": "op_checkpoint_save_001",
  "agent_did": "did:memo:agent:example",
  "instance_id": "instance_example",
  "run_id": "run_20261016_001",
  "delegation_id": "dlg_example",
  "namespace": "project/a",
  "operation": "write",
  "purpose": "continue_project_work",
  "expected_parent_version": "v_003",
  "object": {
    "schema_version": "memo.state_object/1",
    "object_id": "chk_project_a_001",
    "type": "checkpoint",
```

**Response example**: the example below shows that the business write succeeded, the receipt material can be obtained, and the background proof is in the processing queue. An `available` receipt or proof means only that the material can be obtained, and the client still needs to verify the signature or proof by type.

```json
{
  "request_id": "req_example_001",
  "operation_id": "op_checkpoint_save_001",
  "decision": "allow",
  "business_status": "succeeded",
  "object_id": "chk_project_a_001",
  "version": "v_004",
  "commitment": {
    "algorithm": "sha256",
    "scope": "ciphertext",
    "value": "<digest>"
  },
  "receipt_id": "rcpt_example",
  "receipt_status": "available",
  "proof_status": "pending"
}
```

`proof_status=pending` means the proof is in the queueing, generation or anchoring flow and cannot by itself prove that the business has succeeded; in this example the write success is expressed by `business_status=succeeded`. Clients should handle business, receipt and proof statuses separately, and must not redo a successful write because of a delay in background anchoring or storage proofs. `decision=allow` expresses only that the policy permitted the request, and it may remain `allow` even if the storage or an external service fails to execute.

| Field                    | Meaning and constraints                                                                                                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request_id`             | Identifier of a request attempt; a retry forms a new request attempt record                                                                                                               |
| `operation_id`           | Identifier of the same retryable business operation; corresponds to the `Idempotency-Key` and is retained when the same operation is retried                                              |
| `instance_id` / `run_id` | Execution instance / one task run; not substitutable for each other                                                                                                                       |
| `receipt_id`             | Identifier of a signed receipt; not equivalent to a request, business operation or task identifier                                                                                        |
| `business_status`        | `not_executed`, `succeeded`, `failed`, `unknown`; for an unknown result, query and reconcile first                                                                                        |
| `receipt_status`         | `available`, `pending`, `failed`; declared available only when the material can actually be obtained                                                                                      |
| `proof_status`           | `not_requested`, `pending`, `available`, `failed`; material being obtainable does not mean verification passed                                                                            |
| `payment_status`         | MEMO settlement status mapping: `not_required`, `required`, `verified`, `settled`, `failed`, `unknown`, `refund_pending`, `refunded`; independent of business, receipt and proof statuses |

The same `operation_id` cannot be reused for a new operation with different content. `v_004` is simply the opaque version string returned by the server in this example, and does not mean the client can derive the next version from `v_003`.

This interface carries the request signature envelope generated by the SDK in the `Memo-Request-Proof` header; the signature format, key identifier and canonicalization rules are fixed by the request proof configuration. The envelope binds the principal, instance, service audience, network domain, method and target, the digest of the canonicalized business payload, `operation_id`, the request time window and an independent `request_nonce`. Gateway uses the signing public key bound to the Agent DID to verify the envelope, the time window and the uniqueness of the nonce. The `nonce` in a delegation is used only for deduplication at issuance registration, and a valid delegation can be used many times within its scope and term; `request_id` is used for log correlation and is verified separately from the request proof.

A legitimate retry generates a new `request_id`, request time and `request_nonce`, and retains the `operation_id` and `Idempotency-Key`. The business ledger atomically registers the idempotency key, the stable business fingerprint and the execution status by Owner, namespace and business operation domain; the fingerprint covers the target, action, purpose, version precondition, payload commitment and billing intent, and excludes per-request identifiers, request time, signatures and tokens. The same key with the same fingerprint reuses the existing execution status, and the same key with a different fingerprint returns a conflict; concurrent requests use atomic placeholders to prevent duplicate execution. When returning an existing result or querying operation status, the current delegation, purpose and revocation status are still revalidated.

**Client requirements**:

* Provide an idempotency key corresponding to `operation_id` for repeatable writes, and distinguish each `request_id`;
* Use `expected_parent_version` or an ETag to avoid silent overwriting;
* Verify the actual signature and schema version of the receipt or response, and the commitment under the specified algorithm and scope;
* Retry only errors explicitly marked as retryable;
* Do not output tokens, private keys, plaintext state or complete authorization credentials in logs.

## 4.1.3 Error Handling, Examples and Acceptance

The error interface returns status and stable error codes separately for business, receipt, proof and settlement. Clients distinguish "the request was not executed," "execution failed," "the execution result is unknown," and "business succeeded, evidence being processed," and choose the query, rejection, backoff or compensation path from the table below, avoiding duplicate operations and duplicate charges.

| Category        | Example errors                             | Client action                                                                                                                                          |
| --------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Authentication  | `IDENTITY_INVALID`, `SIGNATURE_EXPIRED`    | Re-authenticate without automatically expanding permissions                                                                                            |
| Delegation      | `DELEGATION_MISSING`, `DELEGATION_REVOKED` | Stop this operation; submit a new request only after obtaining an independent valid delegation signed by the Owner                                     |
| Policy          | `PURPOSE_NOT_ALLOWED`, `OPERATION_DENIED`  | Do not retry; show the minimal denial reason                                                                                                           |
| Object          | `OBJECT_NOT_FOUND`, `VERSION_CONFLICT`     | Check the visible scope; deduplicated append, field merge or retention of an isolated branch by rule                                                   |
| Storage         | `BACKEND_UNAVAILABLE`, `WRITE_NOT_DURABLE` | Query the business status for the operation\_id first, then back off under idempotency rules; report success only after persistence conditions are met |
| Receipt         | Local receipt recovering or save failed    | Query or recover the record by receipt\_status; business that has already succeeded must not be repeated because of it                                 |
| Proof           | `PROOF_PENDING`, `ANCHOR_DELAYED`          | Poll or subscribe asynchronously, and do not roll back business that has succeeded                                                                     |
| External action | `SIDE_EFFECT_UNKNOWN`                      | Reconcile first, and do not retry blindly                                                                                                              |

An automated validation configuration contains the component version, environment, input samples, expected output, allow and deny paths, retry rules, cost limit, cleanup scope and assertions. The validator executes requests in an isolated namespace and checks version, permission, idempotency and recovery semantics against the results; the cleanup job handles only the objects and restricted credentials created by that validation run.
