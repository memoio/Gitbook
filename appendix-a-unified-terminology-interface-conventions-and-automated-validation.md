# Appendix A: Unified Terminology, Interface Conventions and Automated Validation

This appendix defines product naming, identity and state terminology, role responsibilities, the configuration model, interface contracts and automated validation rules. Components exchange requests, objects and evidence under shared contracts, and deployment parameters are resolved through the configuration mechanism in [Appendix B](/broken/pages/be6896e742ac84976411145f54b8ba4b00ca8727).

## A.2 Identity, State and Evidence Terminology

| Term                 | Definition                                                                                                                  | Technical boundary                                                                                                                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User Identity        | The identity of the person or organization that bears final responsibility for data, keys and authorization                 | Kept separate from the identity of the Agent that accepts a delegation                                                                                                                                   |
| Agent (logical role) | A persistent agent service, role or business principal                                                                      | Can be associated with multiple models, execution instances and Agent DIDs                                                                                                                               |
| Agent DID            | An identifier for the executing principal, binding an Agent identity signing public key to an execution instance            | Changes to the model or metadata do not create a new DID; replacing the identity signing key creates a new instance and a new DID                                                                        |
| Agent Instance       | An execution instance identified by `instance_id` that uses a fixed identity signing key                                    | The DID is preserved when the same instance identifier and signing key are recovered under control; regenerating the identity key creates a new instance; concurrent instances are identified separately |
| Run                  | One task execution or resumed execution, identified by `run_id`                                                             | A resumed execution creates a new `run_id` and references the source Checkpoint, keeping a verifiable run association                                                                                    |
| Agent Signing Key    | The key used for Agent control proofs and request signatures                                                                | Old and new identities are linked by a continuity record, and the Owner issues a delegation for the new DID; historical credentials keep the original issuer and the old Agent DID recorded in them      |
| Data Encryption Key  | The key used to encrypt and decrypt Vault object or namespace content                                                       | Rotation does not change the Agent DID; the rotation record links the key version, object versions and conversion receipts                                                                               |
| Binding              | A relationship established jointly by the Owner's signed statement and the Agent's proof of control                         | A binding expresses an identity association; authorization for actions is specified separately by delegation                                                                                             |
| Delegation           | Permission granted by the Owner for an Agent to perform actions within a specified scope, term and conditions               | Gateway automatically verifies signatures and checks purpose, resource, action, quota, term and revocation status                                                                                        |
| Policy               | Versioned rules that evaluate subject, resource, action, environment, cost and risk                                         | Decisions use a pinned policy version and output the matched rule, the result and a reason code                                                                                                          |
| Memory               | Information extracted by source and purpose, validated by admission rules and reused by later tasks                         | Admission means the policy is satisfied; it does not automatically establish the content as fact                                                                                                         |
| Candidate Memory     | Candidate information entering the memory admission process                                                                 | Stored separately from admitted memory; admitted, rejected or quarantined according to validation results                                                                                                |
| State Object         | A general state object with an identifier, type, version, content reference, policy and provenance                          | Can carry Memory, Checkpoint, Trace, Artifact and other kinds of state                                                                                                                                   |
| Checkpoint           | A consistent recovery snapshot of task state, object versions and external dependencies                                     | Versions, dependencies, tool permissions and side-effect status are validated before recovery                                                                                                            |
| Version              | An immutable object version assigned by the server and identified by an opaque string                                       | `parent_refs` records the direct parent versions; read order and branch relationships are not inferred from string ordering                                                                              |
| Trace                | Run steps, tool calls, input and output references, and event relationships                                                 | Observable execution information is stored under the minimal-record principle; the full hidden reasoning process is not stored by default                                                                |
| Artifact             | A result produced by an Agent that is validated, delivered or reused according to task rules                                | Result acceptance rules are applied separately from provenance, storage and access evidence                                                                                                              |
| Memory Pack          | A migration or handoff package consisting of a manifest, objects, provenance and key wrapping                               | Trimmed to the recipient's authorization; digest, schema, purpose and version relationships are validated on import                                                                                      |
| Handoff              | The process of delegating a task and the minimum necessary state to another principal                                       | The recipient uses an independent delegation, and the source object's ownership and retention policy remain in force                                                                                     |
| Provenance           | A structured record of source, generating principal, instance, run, transformation, dependencies, time and admission status | `parent_refs` records direct parent versions only; source credibility is assessed by type and evidence rules                                                                                             |
| Commitment           | A check value bound to a defined content scope, containing `algorithm`, `scope` and `value`                                 | Digests of identical ciphertext are comparable; re-encryption or format conversion produces a new digest and records the mapping; a plain hash does not by itself provide content confidentiality        |
| Receipt              | A record issued by an issuer for events such as a request, a policy decision and an operation result                        | Signature verification checks the issuer and the integrity of the statement; business results and log integrity are verified under their own rules                                                       |
| Storage Proof        | Evidence for a claim about retention, availability or a sampled response                                                    | The verification scope is bounded by the proof type, challenge parameters and data commitment                                                                                                            |
| Runtime Evidence     | Evidence associated with the runtime principal, environment, input and output digests, tools and results                    | Trimmed according to privacy policy and bound to `run_id`, object version and issuer                                                                                                                     |
| Attestation          | A signed statement by an issuer about a specific claim                                                                      | Verification checks the issuer's qualification, the claim scope, validity period and referenced evidence                                                                                                 |
| Audit Root           | The root digest formed from a batch of audit events                                                                         | An inclusion proof verifies that a member is consistent with the root; sequence numbers, ranges and continuity checks address the risks of omission and duplication                                      |
| Proof Registry       | An append-only registry that indexes evidence references by `(object_id, version)`                                          | `proof_refs` stores the evidence snapshot at object creation; later evidence is written to the registry without rewriting the immutable object body                                                      |

MEMO's own schemas and interface fields use `snake_case`; HTTP headers, external protocols and ABIs keep their native names. The State Object contract is in [8.1.1](file:///5907924/08-reference-economics/8-1-dev-reference.md#c8-1-1), and the operation statuses are in [4.1.2](file:///5907924/04-developer-guide/4-1-quickstart.md#c4-1-2). `confirmation_status: confirmed` means the memory passed the admission policy named by `confirmation_policy_ref`, `confirmation_method: policy_validation` indicates automated validation, and `confirmed_by` records the identity of the policy service. This field expresses the admission result; the truthfulness of the content is judged separately through provenance verification and task acceptance rules.

## A.3 Unified Roles

| Unified role     | Responsibility                                                    | Permission constraints                                                                                                               |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| User / Owner     | Controls data, identity bindings, delegations and policy          | Defines the execution scope through signed authorization; keys and permissions are managed according to the deployment configuration |
| Agent            | The logical principal that accepts delegations and performs tasks | Requests are initiated by a specific Agent Instance                                                                                  |
| Agent Instance   | Executes tasks using an `instance_id` and an Agent DID            | Every request carries a valid delegation; tasks are distinguished by `run_id`                                                        |
| Storage Provider | Provides capacity, stores data and responds to proofs             | Acts according to orders, retention policy and challenge requirements; storing ciphertext does not confer decryption rights          |
| Guardian         | Coordinates orders, challenges, credentials and repair            | The name Keeper is resolved to Guardian through role mapping; the authorization scope follows the protocol configuration             |
| Verifier         | Verifies proofs, statements or run results                        | Loads parameters and trust anchors by verification type; configured separately from Guardian permissions                             |
| Attester         | Issues an Attestation for a specific claim                        | The claim is bound to an evidence scope, a signing key and a validity period                                                         |
| Operator         | Performs operation or aggregation work for systems such as Meeda  | The identity carries a product and responsibility namespace and is distinguished from the user's Agent operating principal           |
| Facilitator      | Verifies payments and executes settlement                         | Reads payment requirements and authorization; resource permission is decided independently by Gateway                                |
| Auditor          | Inspects events, proofs and control effectiveness                 | The audit license limits the objects, time and evidence scope; plaintext access requires separate authorization                      |
| Policy Engine    | Executes admission, permission, conflict and risk rules           | Records the rule version, input digest and decision result; rejects or quarantines on failure                                        |

## A.4 Product Configuration and Runtime Status

Products express capability combinations through responsibilities and deployment configuration. A service manifest contains `component_id`, `component_version`, `environment`, `api_version`, `schema_versions`, `feature_set`, `backend_types`, `auth_methods` and `policy_refs`; clients use it for discovery, version negotiation and permission checks.

| Configuration dimension    | Values or structure                                                              | Enforcement rule                                                                                                                                                                                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Product components         | Protocol, Vault, Gateway, Proof and extension adapters                           | Each component declares its interfaces, dependencies, inputs and outputs, and trust boundary                                                                                                                                                                             |
| Storage backends           | `local`, `hosted`, `mefs`                                                        | A stable `content_ref` is resolved to the physical backend through a location mapping; migrating ciphertext as-is preserves the object version, while re-encryption or format conversion creates a new version and records the commitment mapping and conversion receipt |
| Interface capabilities     | Versioned `feature_set` and action set                                           | The negotiated result bounds the callable actions; a request is rejected with a reason code when a required capability is missing                                                                                                                                        |
| Identity and authorization | Identity resolution, Owner binding, delegation, policy and revocation references | Validated against the currently effective policy; neither payment nor registration substitutes for access authorization                                                                                                                                                  |
| Evidence modes             | Local receipts, audit aggregation, on-chain anchoring, storage proofs            | Selected by claim and privacy policy; issuance conditions and trust anchors are fixed by the configuration                                                                                                                                                               |
| Runtime environments       | Development, integration testing, isolated production namespaces                 | Keys, service addresses, payment networks and object namespaces are isolated from each other                                                                                                                                                                             |

| Status field          | Values                                                                                                      | Handling                                                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `decision`            | `allow` / `deny`                                                                                            | Records the policy decision, returned separately from the business result                                                                          |
| `business_status`     | `not_executed` / `succeeded` / `failed` / `unknown`                                                         | A successful result is reused by idempotency key; an unknown result is queried and reconciled, keeping side effects mutually exclusive             |
| `receipt_status`      | `available` / `pending` / `failed`                                                                          | The receipt is retrieved or reissued by operation ID without triggering a redo of the business action                                              |
| `proof_status`        | `not_requested` / `pending` / `available` / `failed`                                                        | Background aggregation, anchoring and retry, or a verification error is returned; availability and successful verification are recorded separately |
| `payment_status`      | `not_required` / `required` / `verified` / `settled` / `failed` / `unknown` / `refund_pending` / `refunded` | MEMO's internal normalized payment status; external protocols and settlement results are mapped through adapters                                   |
| `confirmation_status` | `candidate` / `confirmed` / `rejected` / `quarantined`                                                      | Memory is checked for provenance, signature, schema, purpose and conflicts, then admitted, rejected or quarantined by rule                         |

## A.5 Naming Conventions and Capability Boundaries

### A.5.1 Naming, Numbering and References

* Product names use the fixed spellings in [A.1](appendix-a-unified-terminology-interface-conventions-and-automated-validation.md#a-1); identifiers, fields and enumerations keep their prescribed case.
* Native fields use `snake_case`; external HTTP headers and protocol fields are mapped through adapters.
* `object_id`, `version`, `instance_id`, `run_id`, `request_id`, `operation_id` and `receipt_id` denote different entities and are not interchangeable.
* Chapters are numbered `1`, `1.1` and `1.1.1`; fixed anchors support references from the table of contents, figures and interfaces.
* Evidence references are bound to an object version, an issuer and a claim scope; the indexing relationship does not change object ownership or authorization.

### A.5.2 Capability and Permission Boundaries

| Concept                 | Technical rule                                                                                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Identity and binding    | The Owner's signed binding statement and the Agent's proof of control are verified separately; registration only serves discovery and identity indexing                                          |
| Identity and keys       | Replacing the identity key creates a new instance and a new DID linked by a continuity record; rotating the data key keeps the DID                                                               |
| Three planes            | Control, data and proof are layered by responsibility; processes, key holders, administrative privileges and issuance trust conditions are isolated through deployment configuration             |
| State admission         | Candidate memory enters the readable set after passing the rules; conflicts are handled by merge, deduplicated append, branch retention or quarantine rules                                      |
| Export and handoff      | An export forms an event, and the recipient obtains a separate scoped license; the source object continues to be managed under its own lifecycle                                                 |
| Proof                   | Provenance, inclusion, storage, runtime and result rules are verified separately; each kind of evidence states its claim and verification conditions                                             |
| On-chain and off-chain  | State plaintext is stored encrypted off-chain; the chain records only the necessary commitments, registrations, proofs and settlement information                                                |
| Protocol adaptation     | Client version, transport, authentication, feature set and mapping rules make up the compatibility configuration and are validated automatically at handshake                                    |
| Payment and access      | Payment is verified and settled first, then the access policy is rechecked and the resource delivered; a failed delivery triggers refund or reversal compensation                                |
| Deletion and revocation | Deletion removes controlled copies and the corresponding keys; revocation constrains subsequent managed access; disclosed plaintext and on-chain digests are handled within their own boundaries |
| Selective assetization  | Executed under the Owner-signed license for objects, rights and purposes; reading, training, resharing and trading are authorized separately                                                     |
| External side effects   | Use independent action permissions, purpose and quota limits, idempotency keys, Checkpoints and compensation rules; a failed risk gate results in rejection                                      |

### A.5.3 Component Capability Contract

| Contract field                       | Content                                                                       | Automated handling                                                                 |
| ------------------------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `component_id` / `component_version` | Component identifier and version                                              | Locates the component in the registry and checks version constraints               |
| `feature_set` / `operation_set`      | Feature and action sets                                                       | Negotiated at handshake and intersected with the delegated actions                 |
| `schema_versions`                    | Input and output structures and compatibility range                           | Schema validation before and after serialization                                   |
| `policy_refs`                        | Access, admission, retention, billing and risk policies                       | Validates signatures, validity periods, applicable objects and policy dependencies |
| `trust_profile`                      | Key holder, decryption location, trust anchors and issuance conditions        | Checks deployment identity, key references and proof eligibility                   |
| `failure_policy`                     | Rules for timeout, rejection, retry, idempotency, quarantine and compensation | Selects a deterministic handling path by operation result and side-effect status   |
| `validation_profile`                 | Contract validation and fault injection rule sets                             | Records the result, component version and configuration digest                     |

## A.6 Component Interfaces and Automated Execution Contract

Each component interface consists of positioning, input, control, output, failure semantics and observability metrics. On request entry, Gateway resolves the interface contract, verifies the principal and delegation, and then calls the component; the component returns the business status by idempotent operation identifier, and the evidence flow advances asynchronously under its own status.

| Contract element               | Content defined                                                                         | Enforcement requirement                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Positioning and responsibility | The problem solved, callers, downstream dependencies and state ownership                | Responsibilities are connected through explicit interfaces                                          |
| Input and preconditions        | Schema, object version, identity, delegation, policy references and request context     | Structure, signature, validity period, scope and version preconditions are validated first          |
| State changes                  | Semantics of read, write, branch, commit, export and delete                             | Changes are tied to idempotency records and immutable versions through `operation_id`               |
| Output and postconditions      | Business result, object references, reason code and evidence references                 | Business, receipt, proof and payment statuses are returned separately                               |
| Failure and recovery           | Rejection, timeout, partial completion, unknown results and dependency failures         | Use query, reconciliation, bounded retry, compensation or quarantine without repeating side effects |
| Security and privacy           | Decryption location, data minimization, purpose control and external action permissions | Enforced under Owner policy; plaintext and key flows stay within the authorized boundary            |
| Validation and observability   | Checks, metric definitions, and log and evidence association                            | Configuration digest, rule version, result and time range are collected automatically               |

Configuration parameters come from the signed registry and the policy repository. When the loader finds a missing item, an expired signature, conflicting versions or an invalid scope, it returns a deterministic error; the relevant component is started only with a configuration that meets the conditions, so invalid parameters never reach business execution.

## A.7 Figure Style and Drawing Prompt Specification

All formal figures are **16:9 landscape, academic-paper-style diagrams**: a pure white background with black text, black outlines and black connectors only; color, gray fills, gradients, shadows, 3D and decorative illustration are prohibited. Use regular rectangles, a uniform line weight and generous whitespace, and output **3840 × 2160 black-and-white 4K PNG or editable SVG**.

* Organize content on a regular grid with a layered layout; keep node interiors pure white; limit each row to five primary nodes, and layer or partition complex relationships.
* Use a clear, consistent typeface and size hierarchy for text; English product names, field names and protocol names keep their exact spelling, and text must not overlap connectors.
* Keep arrows and borders at a uniform line weight; distinguish relationships through solid lines, dashed lines, numbering and text labels, not through color, fill or weight.
* Node names, directions, relationships, conditions and state transitions must match the figure source; do not add undefined products, automatic authorization, payment guarantees or verification conclusions.
* Express the control plane, data plane, proof plane, organization and on-chain/off-chain boundaries with unfilled rectangular zones and text labels.
* Order sequence diagrams by the actual message order, marking policy decisions, payment, business execution, receipts and asynchronous proofs separately.
* State diagrams keep the existing transitions, rollbacks, self-loops and end points; express conditions through rectangular nodes or connector labels.
* Distinguish keys, plaintext, encrypted content, commitments and proofs; figures must not imply that plaintext goes on-chain or that all deployments have the same isolation capability.

All figures maintain nodes and connections in Mermaid sources and are rendered according to this section; each figure also has a complete prompt with a "Drawing style" part and a "Drawing content" part that can be copied independently, collected in [Appendix C](/broken/pages/c5b2c1674b5943f180c2ff937554b1c075f87123). See the [Figure Index](file:///5907924/preface/figure-index.md) for the list of figures.

## A.9 Automated Validation and Runtime Checks

The validation pipeline runs structural, permission, data, payment, proof and recovery checks according to interface contracts and deployment configuration. Every record is associated with `component_version`, `schema_version`, `config_digest`, `test_case_id`, an input digest, the result and the execution time; a failed result blocks the corresponding configuration from business routing, and recovery uses a configuration version that has passed the same contract checks.

| Validation domain        | Automated checks                                                                                                                            | Failure handling                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Structure and references | Chapter anchors, table of contents, figure numbers, figure and text labels, code blocks, JSON / YAML and schemas                            | Outputs the location and rule number and blocks the invalid document or configuration artifact                            |
| Names and roles          | Product names, identity granularity, action names, identifier types and role mappings                                                       | Rejects mixed-up identifiers and out-of-bounds role mappings                                                              |
| Identity and delegation  | Proof of control, Owner binding, signatures, scope, expiry, revocation, and continuity between old and new identities                       | Rejects the request and records a reason code; recovery statements are verified through an independent authorization path |
| State and provenance     | Object immutability, direct parent versions, version conflicts, admission rules, source references and ciphertext digests                   | Keeps the valid version, merges or quarantines conflicts by rule, and rejects corrupted content                           |
| Idempotency and faults   | Retries, timeouts, disconnections, receipts lost after success, and unknown payment or business results                                     | Queries and reconciles by `operation_id`, suppressing duplicate writes and duplicate settlement                           |
| Receipts and Proof       | Signature verification, event sequence, aggregation intervals, duplicate detection, inclusion proofs, evidence freshness and issuance scope | Quarantines non-conforming evidence, re-aggregates or fetches materials again, and keeps business status independent      |
| Keys and deployment      | Key holder location, decryption boundary, key versions, environment isolation, backup retention and revocation propagation                  | Blocks non-conforming deployments or access, and performs rotation, controlled recovery and audit recording               |
| Payment and metering     | Quote signatures, unit price versions, metering units, budgets, idempotency, and the linkage of settlement, delivery and compensation       | Rejects over-quota requests, queries orders and reconciles, and refunds or reverses by compensation rules                 |
| Adaptation and network   | Protocol handshake, version sets, transport, authentication, chain ID, ABI, endpoint identity and capability manifest                       | Disables mismatched routes and returns a compatibility or network configuration error                                     |
| Migration and recovery   | Manifest, authorization trimming, re-encryption mapping, version dependencies, Checkpoints, rollback and external side effects              | Quarantines the import package or recovery session and preserves the source version and recovery point                    |

Runtime checks are counted separately from business operations. When a validation fails, the explicit failure status, the matched rules and the evidence references are retained; successful payment, a reachable interface or the existence of a record cannot substitute for a validation result.

## A.10 Completeness Constraints for the Technical Design

A component specification includes product responsibilities, interfaces and object schemas, identity and authorization, keys and trust boundaries, state transitions, exception handling, metering, compatibility, migration and validation rules. Every configurable parameter is bound to its resolution source, type, allowed range, validity period and failure action; every state change is bound to its preconditions, outputs and evidence; every asynchronous task is bound to an operation index, a query entry point, retry constraints and termination conditions.

Documentation and runtime configuration use the same terms, fields, actions and version references. Figures express component relationships and event order, while the prompts accompanying the figures specify a unified drawing style and the complete content; structural checks keep figures, text, interface examples and configuration references consistent with one another.
