# 附录 A：统一术语、接口约定与自动验证

本附录定义产品命名、身份与状态术语、角色职责、配置模型、接口契约及自动化验证规则。各组件按共同契约交换请求、对象和证据，部署参数通过[附录 B](/broken/pages/988349c2527630e89cc072c4783bfe4603895f19)的配置机制解析。

## A.1 产品与品牌命名

| 标准名称                   | 中文或简称          | 产品定位                      | 核心连接关系                              |
| ---------------------- | -------------- | ------------------------- | ----------------------------------- |
| MEMO                   | MEMO           | 项目与品牌总称                   | 组织协议、产品与基础设施                        |
| MEMO Agent State Layer | MEMO Agent 状态层 | 面向 Agent 长期任务与协作的可携状态基础设施 | 连接身份、状态、授权、证据、计算和结算                 |
| MEMO Protocol          | Protocol       | 协议与网络底座                   | 为 Vault、Gateway、Proof 提供共同机制        |
| MEMO Vault             | Vault          | 状态对象与多后端存储                | 管理 Local、Hosted、MEFS 的对象、版本、加密与生命周期 |
| MEMO Agent Gateway     | Gateway        | 身份、委托与策略执行入口              | 接收请求、检查权限、调用后端并签发回执                 |
| MEMO Proof             | Proof          | 存储、访问、来源与运行证据层            | 采集凭证、聚合审计根、索引证据与执行核验                |
| MEFS                   | MEFS           | 去中心化存储网络                  | 承接长期保存、冗余、修复与存储证明                   |
| Data Wallet            | Data Wallet    | 用户身份、密钥与数据控制入口            | 管理 Owner 绑定、委托、策略和密钥封装              |
| Data Market            | Data Market    | 数据与状态的选择性交付               | 按许可范围组织发现、报价、授权、交付和结算               |
| Meeda                  | Meeda          | 数据可用性与存储证明方案              | 对接 Lightnode、FileProof、链上验证与挑战      |
| DataDrive              | DataDrive      | 文件与数据管理应用                 | 通过文件适配器连接存储 API 与 Vault 对象模型        |

**MEMO Protocol 定义共同机制；Vault 保存状态；Gateway 执行身份、委托与访问策略；Proof 组织可核验证据。** 存储、数据可用性、用户控制和市场交付组件通过适配器与注册表接入上述产品边界。

## A.2 身份、状态与证据术语

| 中文 / 英文                          | 定义                                          | 技术边界                                                      |
| -------------------------------- | ------------------------------------------- | --------------------------------------------------------- |
| 用户身份 / User Identity             | 对数据、密钥和授权承担最终控制责任的人或组织身份                    | 与接受委托的 Agent 身份分开                                         |
| Agent / 逻辑角色                     | 持续存在的 Agent 服务、角色或业务主体                      | 可关联多个模型、执行实例和 Agent DID                                   |
| Agent DID                        | 绑定 Agent 身份签名公钥与执行实例的执行主体标识                 | 模型和元数据变化不创建新 DID；身份签名密钥更换创建新实例与新 DID                      |
| 执行实例 / Agent Instance            | 由 `instance_id` 标识、使用固定身份签名密钥的执行实例          | 同一实例标识和签名密钥受控恢复时保持 DID；重新生成身份密钥时形成新实例；并发实例分别标识            |
| 任务运行 / Run                       | 由 `run_id` 标识的一次任务执行或恢复执行                   | 恢复执行创建新的 `run_id` 并引用来源 Checkpoint，保持可核验的运行关联             |
| Agent 身份签名密钥 / Agent Signing Key | 用于 Agent 控制权证明和请求签名的密钥                      | 新旧身份以连续性记录关联，Owner 为新 DID 签发委托；历史凭证保留原签发者及记录中的旧 Agent DID |
| 数据加密密钥 / Data Encryption Key     | 用于 Vault 对象或命名空间内容加解密的密钥                    | 轮换不改变 Agent DID；轮换记录关联密钥版本、对象版本与转换回执                      |
| 绑定 / Binding                     | Owner 签名声明与 Agent 控制证明共同建立的关系               | 绑定表达身份关联，动作授权由委托单独规定                                      |
| 委托 / Delegation                  | Owner 授予 Agent 在指定范围、时限与条件下执行动作的权限          | Gateway 自动验签并校验用途、资源、动作、额度、期限和撤销状态                        |
| 策略 / Policy                      | 对主体、资源、动作、环境、费用与风险进行评估的版本化规则                | 决策使用固定策略版本，输出命中规则、结果及原因码                                  |
| Memory                           | 按来源和用途提取、经准入规则校验后供后续任务复用的信息                 | 准入表示满足策略，不等于内容事实自动成立                                      |
| Candidate Memory                 | 进入记忆准入流程的候选信息                               | 与已准入记忆分区存储；按校验结果准入、拒绝或隔离                                  |
| State Object                     | 具有标识、类型、版本、内容引用、策略和来源的通用状态对象                | 可承载 Memory、Checkpoint、Trace、Artifact 等                    |
| Checkpoint                       | 对任务状态、对象版本和外部依赖形成的一致恢复快照                    | 恢复前校验版本、依赖、工具权限和副作用状态                                     |
| Version                          | 由服务端分配、以不透明字符串标识的不可变对象版本                    | `parent_refs` 记录直接父版本；读取顺序和分支关系不由字符串排序推断                  |
| Trace                            | 运行步骤、工具调用、输入输出引用和事件关系                       | 按最小记录原则保存可观察执行信息，默认不保存完整隐藏思维过程                            |
| Artifact                         | Agent 产生并按任务规则校验、交付或复用的结果                   | 结果验收规则与来源、存储及访问证据分别执行                                     |
| Memory Pack                      | 由 manifest、对象、来源和密钥封装组成的迁移或交接包              | 按接收方授权裁剪，导入时校验摘要、Schema、用途与版本关系                           |
| Handoff                          | 将任务与最小必要状态受权交给另一主体的过程                       | 接收方使用独立委托，源对象所有权和保留策略持续生效                                 |
| Provenance                       | 对来源、生成主体、实例、运行、变换、依赖、时间和准入状态的结构化记录          | `parent_refs` 仅记录直接父版本；来源可信度按类型和证据规则评估                    |
| Commitment                       | 绑定明确内容范围的校验值，包含 `algorithm`、`scope`、`value` | 对相同密文可比较摘要；重新加密或格式转换生成新摘要并记录映射；普通哈希不单独提供内容保密性             |
| Receipt                          | 签发者对请求、策略决定和操作结果等事件签发的记录                    | 验签核验签发者与声明完整性，业务结果和日志完整性另按相应规则核验                          |
| Storage Proof                    | 对保存、可用性或抽样响应命题提供的证据                         | 验证范围由证明类型、挑战参数和数据承诺限定                                     |
| Runtime Evidence                 | 与运行主体、环境、输入输出摘要、工具和结果关联的证据                  | 依隐私策略裁剪并绑定 `run_id`、对象版本和签发者                              |
| Attestation                      | 签发者对具体声明作出的签名陈述                             | 核验签发者资格、声明范围、时效及引用证据                                      |
| Audit Root                       | 批量审计事件形成的根摘要                                | 包含证明核验成员与根的一致性；序列号、区间与连续性检查处理漏记和重复风险                      |
| Proof Registry                   | 以 `(object_id, version)` 索引证据引用的追加式注册表      | `proof_refs` 保存对象创建时的证据快照；后续证据写入注册表，不改写不可变对象正文            |

MEMO 自有 Schema 和接口字段使用 `snake_case`；HTTP 头、外部协议及 ABI 保留原生名称。State Object 契约见[8.1.1](/broken/pages/d95ebae3d66c3827bd692237f673751b09c18921#c8-1-1)，各类操作状态见[4.1.2](/broken/pages/8a5b481a582195e2bc031837f88b8d24f9555b38#c4-1-2)。`confirmation_status: confirmed` 表示通过 `confirmation_policy_ref` 指定的准入策略，`confirmation_method: policy_validation` 标明自动校验方式，`confirmed_by` 记录策略服务身份。该字段表达准入结果，内容真实性通过来源核验和任务验收规则分别判断。

## A.3 角色统一

| 统一角色             | 职责                                | 权限约束                                  |
| ---------------- | --------------------------------- | ------------------------------------- |
| User / Owner     | 控制数据、身份绑定、委托及策略                   | 通过签名授权定义执行范围，密钥与权限按部署配置管理             |
| Agent            | 接受委托并执行任务的逻辑主体                    | 由具体 Agent Instance 发起请求               |
| Agent Instance   | 使用 `instance_id` 和 Agent DID 执行任务 | 每次请求携带有效委托；任务以 `run_id` 区分            |
| Storage Provider | 提供容量、保存数据并响应证明                    | 依据订单、保存策略和挑战要求执行，不因保存密文获得解密权          |
| Guardian         | 协调订单、挑战、凭证与修复                     | Keeper 名称通过角色映射解析为 Guardian，授权范围按协议配置 |
| Verifier         | 核验证明、声明或运行结果                      | 按验证类型加载参数和信任锚，与 Guardian 权限分别配置       |
| Attester         | 对特定声明签发 Attestation               | 声明绑定证据范围、签发密钥和有效期                     |
| Operator         | 承担 Meeda 等系统的运营或聚合工作              | 身份带产品与职责命名空间，与用户 Agent 操作主体区分         |
| Facilitator      | 验证和执行支付结算                         | 读取支付要求与授权，资源权限由 Gateway 独立判断          |
| Auditor          | 检查事件、证明和控制有效性                     | 审计许可限定对象、时间和证据范围，明文访问另行授权             |
| Policy Engine    | 执行准入、权限、冲突与风险规则                   | 记录规则版本、输入摘要和决策结果，失败时拒绝或隔离             |

## A.4 产品配置与运行状态

产品通过职责和部署配置表达能力组合。服务清单包含 `component_id`、`component_version`、`environment`、`api_version`、`schema_versions`、`feature_set`、`backend_types`、`auth_methods` 和 `policy_refs`；客户端据此完成发现、版本协商与权限检查。

| 配置维度  | 取值或结构                               | 执行规则                                                                  |
| ----- | ----------------------------------- | --------------------------------------------------------------------- |
| 产品组件  | Protocol、Vault、Gateway、Proof 与扩展适配器 | 每个组件声明接口、依赖、输入输出和信任边界                                                 |
| 存储后端  | `local`、`hosted`、`mefs`             | 稳定 `content_ref` 经定位映射解析到物理后端；原样密文迁移保持对象版本，重新加密或格式转换创建新版本并记录承诺映射与转换回执 |
| 接口能力  | 版本化 `feature_set` 与动作集合             | 协商结果限定可调用动作；缺少所需能力时拒绝请求并返回原因码                                         |
| 身份与授权 | 身份解析、Owner 绑定、委托、策略与撤销引用            | 按当前有效策略校验，不由支付或登记替代访问授权                                               |
| 证据模式  | 本地回执、审计聚合、链上锚定、存储证明                 | 按命题和隐私策略选择，签发条件及信任锚随配置固定                                              |
| 运行环境  | 开发、集成验证、隔离生产命名空间                    | 密钥、服务地址、支付网络与对象命名空间相互隔离                                               |

| 状态字段                  | 取值                                                                                                          | 处理方式                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `decision`            | `allow` / `deny`                                                                                            | 记录策略决策，与业务结果分别返回                      |
| `business_status`     | `not_executed` / `succeeded` / `failed` / `unknown`                                                         | 成功结果按幂等键复用；未知结果查询和对账，保持副作用互斥          |
| `receipt_status`      | `available` / `pending` / `failed`                                                                          | 按操作 ID 取回或补发回执，不触发业务动作重做              |
| `proof_status`        | `not_requested` / `pending` / `available` / `failed`                                                        | 后台聚合、锚定、重试或返回核验错误；可获取与验证通过分别记录        |
| `payment_status`      | `not_required` / `required` / `verified` / `settled` / `failed` / `unknown` / `refund_pending` / `refunded` | MEMO 内部标准化支付状态；通过适配器映射外部协议与结算结果       |
| `confirmation_status` | `candidate` / `confirmed` / `rejected` / `quarantined`                                                      | 对记忆执行来源、签名、Schema、用途和冲突检查，按规则准入、拒绝或隔离 |

## A.5 命名约定与能力边界

### A.5.1 命名、编号与引用

* 产品名称采用[A.1](fu-lu-atong-yi-shu-yu-jie-kou-yue-ding-yu-zi-dong-yan-zheng.md#a-1)中的固定写法；标识、字段和枚举保留规定大小写。
* 自有字段采用 `snake_case`，外部 HTTP 头和协议字段使用适配器完成映射。
* `object_id`、`version`、`instance_id`、`run_id`、`request_id`、`operation_id`、`receipt_id` 分别表示不同实体，不能互相代用。
* 章节使用 `1`、`1.1`、`1.1.1` 编号；固定锚点承接目录、图表和接口引用。
* 证据引用绑定对象版本、签发者和声明范围；索引关系不改变对象所有权或授权。

### A.5.2 能力与权限边界

| 概念     | 技术规则                                            |
| ------ | ----------------------------------------------- |
| 身份与绑定  | Owner 签名绑定声明和 Agent 控制证明分别验签；注册仅承担发现与身份索引       |
| 身份与密钥  | 身份密钥更换形成新实例与新 DID，以连续性记录关联；数据密钥轮换保持 DID         |
| 三平面    | 控制、数据和证明按职责分层，进程、持钥方、管理权限与签发信任条件通过部署配置隔离        |
| 状态准入   | 候选记忆通过规则后进入可读取集合，冲突按合并、去重追加、保留分支或隔离规则处理         |
| 导出与交接  | 导出形成事件，接收方获得独立范围许可；源对象按自身生命周期继续管理               |
| Proof  | 分别核验来源、包含关系、存储、运行和成果规则；每类证据标注命题与验证条件            |
| 链上与链下  | 状态原文在链下加密保存，链上记录必要的承诺、登记、证明与结算信息                |
| 协议适配   | 客户端版本、传输、认证、功能集合和映射规则组成兼容配置，握手时自动校验             |
| 支付与访问  | 先验证支付、执行结算，再复核访问策略并交付；交付失败执行退款或冲正补偿             |
| 删除与撤销  | 删除受控副本和相应密钥，撤销约束后续受管访问；已披露明文和链上摘要按各自边界处理        |
| 选择性资产化 | 依据 Owner 签署的对象、权利与用途许可执行；读取、训练、再共享和交易分别授权       |
| 外部副作用  | 使用独立动作权限、用途与额度限制、幂等键、Checkpoint 和补偿规则；风险门控失败即拒绝 |

### A.5.3 组件能力契约

| 契约字段                                 | 内容                  | 自动处理机制              |
| ------------------------------------ | ------------------- | ------------------- |
| `component_id` / `component_version` | 组件标识与版本             | 按注册表定位组件并检查版本约束     |
| `feature_set` / `operation_set`      | 功能与动作集合             | 握手协商并与委托动作求交集       |
| `schema_versions`                    | 输入输出结构及兼容范围         | 序列化前后执行 Schema 校验   |
| `policy_refs`                        | 访问、准入、保留、计费和风险策略    | 校验签名、有效期、适用对象和策略依赖  |
| `trust_profile`                      | 持钥方、解密位置、信任锚和签发条件   | 检查部署身份、密钥引用与证明资格    |
| `failure_policy`                     | 超时、拒绝、重试、幂等、隔离和补偿规则 | 按操作结果及副作用状态选择确定处理路径 |
| `validation_profile`                 | 契约校验与故障注入规则集合       | 记录结果、组件版本和配置摘要      |

## A.6 组件接口与自动执行契约

每个组件接口由定位、输入、控制、输出、失败语义与观测指标构成。Gateway 在请求进入时解析接口契约，验证主体与委托后调用组件；组件按幂等操作标识返回业务状态，证据流程按独立状态异步推进。

| 契约要素    | 定义内容                         | 执行要求                            |
| ------- | ---------------------------- | ------------------------------- |
| 定位与职责   | 解决的问题、调用方、下游依赖和状态归属          | 职责之间通过明确接口连接                    |
| 输入与前置条件 | Schema、对象版本、身份、委托、策略引用和请求上下文 | 先校验结构、签名、时效、作用域和版本前提            |
| 状态变更    | 读取、写入、分支、提交、导出和删除的语义         | 变更以 `operation_id` 关联幂等记录和不可变版本 |
| 输出与后置条件 | 业务结果、对象引用、原因码和证据引用           | 分别返回业务、回执、证明与支付状态               |
| 失败与恢复   | 拒绝、超时、部分完成、未知结果和依赖故障         | 使用查询、对账、受限重试、补偿或隔离，不重复副作用       |
| 安全与隐私   | 解密位置、数据最小化、用途控制、外部动作权限       | 按 Owner 策略执行，明文与密钥流向保持在授权边界内    |
| 验证与观测   | 检查项目、指标定义、日志与证据关联            | 自动采集配置摘要、规则版本、结果与时间范围           |

配置参数来自签名注册表与策略仓库。加载器发现缺项、过期签名、冲突版本或不合法作用域时返回确定错误；使用符合条件的配置启动相应组件，避免将无效参数带入业务执行。

## A.7 图表风格与绘图提示词规范

所有正式插图采用 **16:9 横版科研论文式图**：仅使用纯白背景、黑色文字、黑色轮廓与黑色连线；禁止彩色、灰色填充、渐变、阴影、3D 和装饰性插画。使用规则矩形、统一线宽和充足留白，输出 **3840 × 2160 黑白 4K PNG 或可编辑 SVG**。

* 以规则网格和分层布局组织内容，节点内部保持纯白；每行不超过5个主要节点，复杂关系分层或分区呈现。
* 中文使用清晰、统一的字体与字号层级；英文产品名、字段名和协议名保留准确拼写，避免文字与连线重叠。
* 箭头与边框保持统一线宽，通过实线、虚线、编号和文字标签区分关系，不依赖颜色、填充或粗细差异。
* 节点名称、方向、关系、条件与状态转换必须与图源一致；不得添加未经定义的产品、自动授权、支付保证或验证结论。
* 控制面、数据面、证明面、组织与链上/链下边界用无填充的矩形分区及文字标识表达。
* 时序图按实际消息顺序排列，分别标明策略判断、支付、业务执行、回执与异步证明。
* 状态图保留已有转换、回退、自循环和终点；条件通过矩形节点或连线标签表达。
* 密钥、明文、加密内容、commitment 和 proof 需区分，不以图示暗示原文上链或所有部署具有相同隔离能力。

全部图表以 Mermaid 图源维护节点与连接结构，并依据本节规范渲染成图；每张图另有一份包含“绘图风格”和“绘图内容”的完整提示词，可单独复制使用，汇总于[附录 C](/broken/pages/dc3756763d6ed216587c263a3f0104b4b8291f74)。图表清单见[图表索引](/broken/pages/e3f41be4bcdf5f0fee06d7c1550c7cfddb673fa5)。

## A.8 外部标准基线

外部标准通过版本化适配器连接 MEMO 的身份、状态、授权与结算模型。适配配置固定规范版本、传输、认证、功能集合与字段映射；协议握手和自动化契约检查按这些配置执行。规范引用及适配关系见[7.3.2](/broken/pages/0ae4c7ee5846434c2deb9f1bcbb132952533774b#c7-3-2)和该章官方参考。

| 标准           | 官方入口                                                                                 | 应用边界                                          |
| ------------ | ------------------------------------------------------------------------------------ | --------------------------------------------- |
| ERC-8004     | [Trustless Agents](https://eips.ethereum.org/EIPS/eip-8004)                          | Agent 注册 / 发现、声誉与验证扩展；不替代用户委托                 |
| ERC-7857     | [AI Agents NFT with Private Metadata](https://eips.ethereum.org/EIPS/eip-7857)       | 私有 Agent 元数据的可验证转移、克隆和使用授权；选择性接入              |
| ERC-7829     | [Data Asset NFT](https://eips.ethereum.org/EIPS/eip-7829)                            | 链下数据资产引用与权限表达；不把原文默认上链                        |
| MCP          | [2026-07-28 Specification](https://modelcontextprotocol.io/specification/2026-07-28) | LLM 应用与资源、提示、工具及扩展的标准连接方式                     |
| A2A          | [Agent2Agent Protocol](https://a2a-protocol.org/latest/)                             | Agent 间任务、消息和 Artifact 协作；不保存 MEMO 状态本身       |
| Agent Skills | [Specification](https://agentskills.io/specification)                                | 以 `SKILL.md` 为核心的能力说明和资源包；内容按来源、工具范围和沙箱策略自动校验 |
| x402         | [HTTP 402](https://docs.x402.org/core-concepts/http-402)                             | API 原生支付要求、支付授权和结算响应；不等同于访问授权                 |

## A.9 自动化验证与运行检查

验证流水线按接口契约和部署配置执行结构、权限、数据、支付、证明与恢复检查。每条记录关联 `component_version`、`schema_version`、`config_digest`、`test_case_id`、输入摘要、结果和执行时间；失败结果阻止对应配置进入业务路由，恢复采用已通过相同契约检查的配置版本。

| 验证域       | 自动检查内容                                       | 失败处理                               |
| --------- | -------------------------------------------- | ---------------------------------- |
| 结构与引用     | 章节锚点、目录、图号、图文标签、代码块、JSON / YAML 与 Schema     | 输出位置和规则编号，阻断无效文档或配置制品              |
| 名称与角色     | 产品名、身份粒度、动作名、标识类型与角色映射                       | 拒绝混用标识或越界角色映射                      |
| 身份与委托     | 控制证明、Owner 绑定、签名、作用域、过期、撤销和新旧身份连续性           | 拒绝请求，记录原因码；恢复声明按独立授权路径核验           |
| 状态与来源     | 对象不可变、直接父版本、版本冲突、准入规则、来源引用与密文摘要              | 保留有效版本，冲突按规则合并或隔离，拒绝损坏内容           |
| 幂等与故障     | 重试、超时、断连、成功后回执丢失、支付或业务结果未知                   | 按 `operation_id` 查询与对账，抑制重复写入和重复结算 |
| 回执与 Proof | 验签、事件序列、聚合区间、重复检测、包含证明、证据时效与签发范围             | 隔离不合格证据，重新聚合或补取材料，业务状态独立保持         |
| 密钥与部署     | 持钥位置、解密边界、密钥版本、环境隔离、备份保留与撤销传播                | 阻断不合格部署或访问，执行轮换、受控恢复和审计记录          |
| 支付与计量     | 报价签名、单价版本、计量单位、预算、幂等、结算、交付与补偿关联              | 拒绝超额请求，查单和对账，按补偿规则退款或冲正            |
| 适配与网络     | 协议握手、版本集合、传输、认证、chain ID、ABI、端点身份与能力清单       | 禁用不匹配的路由，返回兼容性或网络配置错误              |
| 迁移与恢复     | manifest、授权裁剪、重加密映射、版本依赖、Checkpoint、回退与外部副作用 | 隔离导入包或恢复会话，保留来源版本和恢复点              |

运行检查与业务操作分开计数。某次验证失败保留明确的失败状态、规则命中和证据引用，不能由支付成功、接口可达或记录存在替代验证结果。

## A.10 技术方案完整性约束

组件规格包含产品职责、接口与对象 Schema、身份授权、密钥与信任边界、状态转移、异常处理、计量、兼容、迁移和验证规则。所有可配置参数绑定解析来源、类型、允许范围、有效期与失败动作；所有状态变更绑定前置条件、输出和证据；所有异步任务绑定操作索引、查询入口、重试约束及终止条件。

文档与运行配置使用相同的术语、字段、动作和版本引用。图表表达组件关系与事件顺序，图下提示词规定统一绘制风格和完整内容；结构检查保证图、正文、接口示例和配置引用相互一致。
