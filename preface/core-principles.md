# core principles

The principles below define the boundaries for product responsibilities, identity granularity, state objects, authorization, evidence and migration; see the relevant chapters for detailed flows and interfaces.

| Topic                                    | Technical principle                                                                                                                                                                                                                                                                                                                                                                                                         | Details                                                                                                                                                                                                                      |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product boundaries                       | Protocol is the protocol and network foundation; Vault manages state and backends; Gateway manages identity, delegation and policy for managed requests; Proof organizes evidence. Vault is not the same as MEFS                                                                                                                                                                                                            | [2.1](file:///5907924/02-core-products/2-1-protocol.md), [2.2](file:///5907924/02-core-products/2-2-vault.md), [3.1](file:///5907924/03-architecture/3-1-overall-architecture.md)                                            |
| Agent identity granularity               | An Agent DID identifies the executing principal at the granularity of "Agent identity signing key + execution instance". The logical Agent, the Agent DID, `instance_id` and `run_id` are kept separate; a change of model or metadata does not by itself create a new DID                                                                                                                                                  | [2.3.1](file:///5907924/02-core-products/2-3-gateway.md#c2-3-1), [5.1.2](file:///5907924/05-security-governance/5-1-identity-policy.md#c5-1-2)                                                                               |
| New identities and the two kinds of keys | Regenerating the Agent identity signing key and forming a new instance creates a new DID; old and new identities are linked by a signed continuity record, and the Owner issues an independent delegation for the new DID. Rotating the Vault data encryption key does not change the DID, and historical credentials keep the original issuer and the old Agent DID recorded in them                                       | [2.2.2](file:///5907924/02-core-products/2-2-vault.md#c2-2-2), [5.1](file:///5907924/05-security-governance/5-1-identity-policy.md)                                                                                          |
| State objects and naming                 | MEMO's own fields uniformly use `snake_case`; the unified State Object carries structured fields such as `provenance`, `parent_refs` and `commitment`. External protocol fields, HTTP headers and real ABIs keep their original spelling                                                                                                                                                                                    | [4.1.2](file:///5907924/04-developer-guide/4-1-quickstart.md#c4-1-2), [8.1.1](file:///5907924/08-reference-economics/8-1-dev-reference.md#c8-1-1)                                                                            |
| Versions and provenance                  | `object_id` is the logical identifier; `version` is an opaque, immutable version string assigned by the server; `schema_version` denotes the structure version. `parent_refs` records only direct parent versions, while provenance and dependencies go into `provenance`; asynchronous evidence is appended to the Proof Registry                                                                                          | [3.2](file:///5907924/03-architecture/3-2-state-model.md), [8.1.1](file:///5907924/08-reference-economics/8-1-dev-reference.md#c8-1-1)                                                                                       |
| Requests and business operations         | `request_id` corresponds to one request attempt; `operation_id` corresponds to the same retryable business operation and is associated with the `Idempotency-Key`; `receipt_id` corresponds to a receipt; `run_id` corresponds to a task run                                                                                                                                                                                | [4.1.2](file:///5907924/04-developer-guide/4-1-quickstart.md#c4-1-2), [8.1.1](file:///5907924/08-reference-economics/8-1-dev-reference.md#c8-1-1)                                                                            |
| Execution status                         | The policy `decision`, the business `business_status`, the receipt `receipt_status`, the proof `proof_status` and, where applicable, `payment_status` are kept separate. Materials being obtainable does not mean they have been verified; waiting for a proof is not a reason to redo a successful write                                                                                                                   | [4.1.2](file:///5907924/04-developer-guide/4-1-quickstart.md#c4-1-2), [8.1.1](file:///5907924/08-reference-economics/8-1-dev-reference.md#c8-1-1)                                                                            |
| Tools and authorized actions             | `create_checkpoint` is a tool name, authorized by `write` and the scope of the Checkpoint resource; read, write, search, import, export, delete, train, share and external actions are expressed as separate permissions                                                                                                                                                                                                    | [4.1.2](file:///5907924/04-developer-guide/4-1-quickstart.md#c4-1-2), [5.1.3](file:///5907924/05-security-governance/5-1-identity-policy.md#c5-1-3)                                                                          |
| x402 call chain                          | After an eligibility pre-check, a 402 is returned; the client retries Gateway carrying the payment authorization, Gateway calls the Facilitator to verify and settle, and the resource authorization is checked again before delivery. If settlement succeeds but delivery fails, compensation applies; an unknown settlement is queried and reconciled first                                                               | [4.2.3](file:///5907924/04-developer-guide/4-2-integrations.md#c4-2-3), [7.1.3](file:///5907924/07-standards/7-1-standards.md#c7-1-3)                                                                                        |
| Three planes and the decryption boundary | The control plane, data plane and proof plane divide responsibilities; actual isolation depends on the deployment, the key holder, the decryption location, operations privileges and the conditions under which proofs are issued                                                                                                                                                                                          | [3.1.1](file:///5907924/03-architecture/3-1-overall-architecture.md#c3-1-1), [3.3](file:///5907924/03-architecture/3-3-trust-boundaries.md)                                                                                  |
| Receipts and Proof                       | A signed receipt records an event claim made by the issuer; inclusion proofs, storage proofs, log integrity and result acceptance are verified separately. Local receipt persistence in Gateway is separate from background Proof aggregation and anchoring                                                                                                                                                                 | [2.4](file:///5907924/02-core-products/2-4-proof.md), [3.1.3](file:///5907924/03-architecture/3-1-overall-architecture.md#c3-1-3), [5.2](file:///5907924/05-security-governance/5-2-provenance-verification.md)              |
| Revocation, export and deletion          | Once confirmed at the relevant policy enforcement points, revocation constrains subsequent controlled access; it cannot recall plaintext that has already been disclosed. An export is an event; authorization, the object lifecycle and the data key status are managed separately                                                                                                                                         | [4.3.3](file:///5907924/04-developer-guide/4-3-lifecycle-operations.md#c4-3-3), [5.3.3](file:///5907924/05-security-governance/5-3-runtime-risk.md#c5-3-3)                                                                   |
| Migration and recovery                   | Migrating the same encrypted envelope as-is preserves the object version and digest, and the backend is switched through a location mapping; re-encryption or format conversion produces a new version and records the old-to-new mapping and the conversion receipt. Cross-model recovery carries over the agreed business state, and recovery rules validate objects, the execution environment and external dependencies | [3.2.3](file:///5907924/03-architecture/3-2-state-model.md#c3-2-3), [6.1.3](file:///5907924/06-infrastructure/6-1-protocol-mefs.md#c6-1-3), [6.3](file:///5907924/06-infrastructure/6-3-app-entry.md)                        |
| On-chain, purpose and assetization       | State plaintext and keys are not publicly put on-chain by default; payment, registration, key custody and business authorization are verified separately. Reading does not automatically include permission to train, reshare, assetize or take external actions; only appropriate objects that the user explicitly chooses enter the assetization flow                                                                     | [3.3.1](file:///5907924/03-architecture/3-3-trust-boundaries.md#c3-3-1), [7.2.3](file:///5907924/07-standards/7-2-proof-collaboration.md#c7-2-3), [8.3](file:///5907924/08-reference-economics/8-3-tokenomics-governance.md) |
